# Hospital Backup Center — คู่มือใช้งาน

ระบบสำรองเฉพาะฐานข้อมูล MariaDB ผ่าน SSH เก็บไฟล์บนเซิร์ฟเวอร์ปลายทาง ไม่สำรองเว็บไซต์และไม่แก้ไขข้อมูลต้นฉบับขณะสำรอง

## เข้าใช้งาน

เปิด http://127.0.0.1:8088 บนเครื่องศูนย์กลาง เข้าสู่ระบบด้วยรหัสผ่านผู้ดูแล เปลี่ยนรหัสผ่านได้ที่เมนูตั้งค่าระบบ

เริ่มเว็บบน Windows:

```powershell
.\.venv\Scripts\python.exe app.py
```

ติดตั้งส่วนประกอบด้วย `pip install -r requirements.txt` และตั้ง `SECRET_KEY` กับ `ADMIN_PASSWORD_HASH` ใน `.env` ตาม `.env.example` ก่อนเริ่มครั้งแรก เก็บ `.env` ให้ปลอดภัย เพราะ SECRET_KEY ใช้ถอดรหัสรหัสผ่าน SSH ที่เก็บใน SQLite ด้วย

## เมนูต่าง ๆ

- หน้าหลัก: ดูผลล่าสุด จำนวนงานสำเร็จวันนี้ และพื้นที่ว่างจริงบนเซิร์ฟเวอร์
- สำรองข้อมูล: สั่งสำรองเครื่องเดียวหรือทุกเครื่อง ระบบป้องกันงานซ้ำในโปรแกรมและใช้ flock บนเครื่องปลายทาง
- ประวัติการสำรอง: ค้นตาม IP และสถานะ เปิด Log และรายละเอียดได้ รายการที่นำเข้าจากเครื่องปลายทางระบุประเภท remote
- ดาวน์โหลดไฟล์: เลือกเซิร์ฟเวอร์ อ่านชุดสำรองที่มี marker สำเร็จ แล้วดาวน์โหลด .sql.gz ผ่าน SSH หน้าเดียวกันนำเข้ารายการสำเร็จจากงานอัตโนมัติเข้าประวัติ โดยไม่เพิ่มรายการซ้ำ ไฟล์ที่ถูกลบตามอายุจะดาวน์โหลดไม่ได้ แต่ประวัติยังคงอยู่
- ตั้งเวลาอัตโนมัติ: อ่านวัน/เวลาและสถานะจริงของ systemd timer เลือกวัน ชั่วโมง นาที เวลาไทย แล้วบันทึก เปิด/ปิด timer ได้โดยไม่สั่งสำรองทันที ดู Log งานอัตโนมัติได้จากหน้านี้
- จัดการเซิร์ฟเวอร์: เพิ่มและแก้ไข IP, Port, User, SSH Key หรือ Password, fingerprint และรายชื่อฐานข้อมูล รหัสผ่านเก็บแบบเข้ารหัส ไม่แสดงกลับบนหน้าเว็บ
- ตั้งค่าระบบ: เปลี่ยนรหัสผ่านผู้ดูแล โดยต้องยืนยันรหัสเดิมและรหัสใหม่อย่างน้อย 12 ตัวอักษร
- แจ้งเตือน: เปิดจากรูปกระดิ่งเพื่อดูงานที่ผิดพลาดหรือยังทำงานอยู่
- พื้นที่จัดเก็บ: อ่านพื้นที่ดิสก์และขนาดโฟลเดอร์สำรองจากเซิร์ฟเวอร์จริง

## เตรียมเครื่องปลายทาง

ติดตั้ง MariaDB client, gzip, Python 3, flock และ systemd

1. อัปโหลด `remote/backup-agent.sh` ไป `/usr/local/sbin/backup-agent.sh` และกำหนด permission 700
2. อัปโหลด `remote/prune-backups.py` ไป `/usr/local/sbin/hospital-backup-prune.py` และกำหนด permission 700
3. สร้าง `/root/.hospital-backup.cnf` permission 600 ด้วยบัญชีฐานข้อมูลที่มีสิทธิ์อ่านตาราง views, routines, triggers และ events ที่ต้องสำรอง

```ini
[client]
user=backup_user
password=YOUR_DATABASE_PASSWORD
```

หาก root ของ MariaDB รองรับ local socket ให้ใช้ `[client]` และ `user=root` โดยไม่ใส่รหัสผ่านได้ ต้องทดสอบก่อนเปิดใช้งาน

4. ยืนยัน fingerprint SSH ผ่านช่องทางที่เชื่อถือได้ก่อนบันทึก รหัสผ่าน SSH กับรหัสผ่าน MariaDB อาจต่างกัน
5. กดทดสอบ SSH แล้วทดลองสำรองและตรวจสอบผล

สำหรับ 10.0.2.16 สคริปต์ตั้งไว้ 8 ฐานข้อมูล: hospital_db, hms, drugalert, drugstock_alert, lr_supplement, medical_request_db, pd_dashboard_db, bed-monitor
สำหรับ 10.0.2.14 ตั้งไว้ 3 ฐานข้อมูล: lr_supplement, ncdappo, nursing_center
สำหรับเครื่องเพิ่มเติม ให้สร้าง `/etc/hospital-backup/databases.list` ใส่ชื่อฐานข้อมูลหนึ่งชื่อต่อบรรทัด ใช้ตัวอักษร ตัวเลข `_` หรือ `-` ให้ root เป็นเจ้าของและ permission 600 รายชื่อในหน้าเว็บต้องตรงกับสคริปต์/ไฟล์บนเครื่องปลายทาง

## เวลาและการเก็บสำเนา

ค่าเริ่มต้นสำรองทุกวันศุกร์ 16:00 น. Asia/Bangkok โดย systemd timer บนเครื่องปลายทาง ไม่จำเป็นต้องเปิดเครื่องศูนย์กลางไว้ หากเครื่องปลายทางปิดในเวลาที่กำหนด จะรันเมื่อเปิดกลับด้วย Persistent timer

ไฟล์ unit อยู่ในโฟลเดอร์ `systemd/` ของโปรเจกต์ ติดตั้งเฉพาะ `hospital-db-backup.*` และ `hospital-db-retention.*` ใน `/etc/systemd/system/` แล้ว daemon-reload และ enable timer ที่พร้อมใช้งาน

เก็บชุดสำรองที่สำเร็จล่าสุดไม่เกิน 3 ชุดต่อเซิร์ฟเวอร์ โดยเรียงตามเวลาสำรองสำเร็จ ลบชุดเก่าสุดหลังรอบใหม่สำเร็จ และตรวจซ้ำทุกวัน 03:00 น. ลบเฉพาะโฟลเดอร์รูปแบบวันที่ซึ่งมี `.hbc-complete` ของระบบ ไม่ตาม symlink ไฟล์เก่าที่ไม่มี marker หรือชุดที่ล้มเหลวไม่ถูกลบอัตโนมัติ นโยบายนี้แทนการเก็บตามอายุ 30 วันเดิม

เมนูลบตามนโยบายแสดงรายการที่เกิน 3 ชุดก่อนลบ ต้องพิมพ์ IP ยืนยัน ไม่มีการลบฐานข้อมูลต้นฉบับ

## ไฟล์สำรอง

```text
/var/backup/hospital-center/YYYYMMDD_HHMMSS/
  databases.sql.gz
  databases.txt
  metadata.txt
  SHA256SUMS
  .hbc-complete
```

สคริปต์ส่งผล `SUCCESS|โฟลเดอร์|ขนาดไฟล์SQL` หลังตรวจ gzip สำเร็จ ศูนย์กลางปฏิเสธ agent รุ่นเก่าที่สำรองเว็บไซต์

ตรวจบนปลายทาง:

```bash
cd /var/backup/hospital-center/YYYYMMDD_HHMMSS
gzip -t databases.sql.gz
sha256sum -c SHA256SUMS
systemctl list-timers hospital-db-backup.timer hospital-db-retention.timer
journalctl -u hospital-db-backup.service -n 100 --no-pager
```

## กู้คืนบนเครื่องทดสอบ

1. เพิ่มเครื่องทดสอบที่แยกจาก production และตั้งค่า SSH/บัญชี MariaDB ให้ครบ
2. ในหน้าจัดการเซิร์ฟเวอร์ ทำเครื่องหมายว่าเครื่องนี้เป็นเครื่องทดสอบสำหรับกู้คืน ห้ามเปิดสิทธิ์นี้บน production
3. เปิดเมนูกู้คืน เลือกเซิร์ฟเวอร์ต้นทาง ชุดสำรอง และเครื่องทดสอบปลายทาง ซึ่งต้องต่างจากต้นทาง
4. ยืนยันรหัสผ่านผู้ดูแลเว็บ และพิมพ์ `RESTORE ตามด้วย IP เครื่องทดสอบ`
5. ระบบตรวจ gzip และ SHA256 ก่อนส่ง SQL เข้า MariaDB ของเครื่องทดสอบ ดูผลในหน้างานกู้คืน

การกู้คืนสร้าง/เขียนทับฐานข้อมูลชื่อเดิมบนเครื่องทดสอบ ต้องเตรียมเครื่องทดสอบให้พร้อมก่อนกด ไม่ควรเปิดสิทธิ์กู้คืนบนเซิร์ฟเวอร์ใช้งานจริง

## ข้อจำกัด

- สำรองใช้ CPU, I/O และพื้นที่ดิสก์บนปลายทาง ควรทำช่วงใช้งานน้อย
- `--single-transaction` เหมาะกับ InnoDB; MyISAM และการเปลี่ยน schema ระหว่างสำรองอาจไม่สอดคล้องกัน
- gzip/SHA256 ผ่านยังไม่เท่ากับทดสอบกู้คืนแล้ว ควรทดสอบกู้คืนและตรวจข้อมูลบนเครื่องทดสอบ
- ควรมีสำเนาแยกเครื่องหรือ offsite เพราะไฟล์บนเครื่องต้นทางอาจเสียหายพร้อมฐานข้อมูล
- ใช้งานผ่านเครือข่ายภายใน/VPN และ HTTPS เมื่อเปิดให้เข้าถึงนอก localhost
- ประวัติงานอัตโนมัตินำเข้าเมื่อเปิดหน้าไฟล์ของเซิร์ฟเวอร์นั้น หากยังไม่มีประวัติ ให้เปิดหน้าไฟล์เพื่อซิงก์ และดู journal ของปลายทางเมื่อมีงานล้มเหลว

## บันทึกการใช้งานและ MFA
เปิดเมนูบันทึกการใช้งาน `/audit` เพื่อค้นเหตุการณ์และส่งออก CSV ประวัติเก็บใน `data/history.sqlite3` แยกจากสำเนาฐานข้อมูลบนเซิร์ฟเวอร์ซึ่งเก็บ 3 ชุด ประวัติการใช้งานเก็บอย่างน้อย 90 วัน ปัจจุบันไม่มีการลบอัตโนมัติ บันทึกเวลา UTC ผู้ใช้ IP ชื่อเมนู วิธี HTTP ผลตอบกลับ และเป้าหมายที่จำเป็น ไม่บันทึกเนื้อหารหัสผ่าน OTP, MFA secret หรือ recovery codes ควรสำรองฐานข้อมูลศูนย์กลางและ `.env` ในที่ปลอดภัยด้วย

ตั้งค่า MFA ที่ `/security/mfa` โดยยืนยันรหัสผ่านผู้ดูแล สแกน QR ด้วย Google Authenticator หรือ Microsoft Authenticator แล้วกรอกรหัส 6 หลัก MFA จะเปิดหลังยืนยันสำเร็จเท่านั้น QR มีอายุ 10 นาที สร้างในเครื่องและไม่ส่ง secret ไปบริการ QR ภายนอก เมื่อเปิดสำเร็จจะแสดง recovery codes 10 รหัสครั้งเดียว แต่ละรหัสใช้ได้ครั้งเดียว ให้เก็บแยกจากโทรศัพท์

เมื่อเปิด MFA การเข้าสู่ระบบต้องผ่านรหัสผ่านก่อน แล้วจึงยืนยัน TOTP หรือ recovery code มีการจำกัดการลอง 8 ครั้งต่อ 5 นาที ป้องกันใช้ OTP counter ซ้ำ และเก็บ secret แบบเข้ารหัสในฐานข้อมูล การเปิด/ปิด MFA หรือเปลี่ยนรหัสผ่านจะยกเลิกเซสชันเก่า ปิด MFA ต้องใช้รหัสผ่านและ TOTP หรือ recovery code ที่ยังไม่ใช้ ห้ามแชร์ QR หรือ secret และต้องสำรอง `.env` เพราะ SECRET_KEY ใช้ถอดรหัส secret/รหัสผ่าน SSH
